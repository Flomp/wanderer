<objective>
Show the user's live position on the elevation profile while navigating a trail in the Flutter app: a vertical guide line plus a dot on the curve at the user's current distance along the track, driven by the same GPS fixes that move the map's location marker, and hidden whenever the user is off the track or no fix has arrived.

Purpose: A hiker following a trail can see their location marker on the map but has no equivalent cue on the elevation profile — they cannot tell whether the climb ahead is the one they are on or the next one. This closes that gap with the same "you are here" affordance the map already has.

Output: `TrackPositionMatcher` (pure, tested) in `app/lib/util/route/`, an opt-in `livePositionMeters` overlay on `ElevationProfile`, and the wiring in `navigation_screen.dart`. Flutter app only — the SvelteKit web app has no live-navigation mode with a location marker (its only `navigate` is the Valhalla proxy endpoint), so there is nothing to mirror there.
</objective>

## Why a second matcher, and why on the GPX rather than the Valhalla shape

`Navigation.onPosition` (navigation_provider.dart) already runs `RouteMapMatcher` and gets an `alongTrackMeters` per fix — but on `NavigateResponse.shape`, which is Valhalla's `trace_route` map-snapped, ≤500-point geometry (see `web/src/routes/api/v1/valhalla/navigate/+server.ts` and `buildNavShape` in `app/lib/util/gpx/gpx.dart`). The chart's x-axis is the RAW cumulative haversine distance over the trail's own GPX points (`buildElevationTrackPoints`, elevation_profile.dart — read the long comment there about raw-vs-smoothed; that axis is also what `Waypoint.distanceFromStart` uses). The two coordinate systems differ in total length and locally, so mapping one onto the other would put the marker visibly off the climb the user is on. Instead, run a second `RouteMapMatcher` over the GPX's own polyline with the chart's own cumulative distances, so the result IS a chart x-coordinate. Per-fix cost is a windowed segment scan (binary-searched), negligible next to what the screen already does per fix.

The matcher is fed the UNSIMPLIFIED track. `buildElevationTrackPoints` thins to 250 points by keeping per-bucket elevation extremes, which cuts corners spatially (chords of hundreds of metres on a long trail) — an on-track hiker on a switchback would read as 100 m off. So Task 2 extracts the walk into `buildRawTrackPoints` and Task 3 feeds that to the matcher; the simplified points keep their original `distanceM`, so both live on the same axis.

## fl_chart 1.2.0 facts verified in the package source (do not re-derive)

- A `LineChartBarData` with exactly one spot is explicitly supported (`generateNormalBarPath` handles `size == 1`) and its dot is drawn by `drawDots` when `dotData.show` is true.
- `barData.show == false` skips the bar entirely (no dots), so it cannot be used to exclude a bar from touch.
- Touch collects the nearest spot from EVERY bar and sorts by pixel distance; `response.lineBarSpots.first` may therefore come from the marker bar. `LineBarSpot` carries `barIndex` and `spotIndex`.
- `getTouchedSpotIndicator(barData, spotIndexes)` receives no bar index; its return type is `List<TouchedSpotIndicatorData?>` (null entries suppress the indicator).
- `VerticalLine(x:, color:, strokeWidth:, dashArray:)` is the existing waypoint-line mechanism in this file.
