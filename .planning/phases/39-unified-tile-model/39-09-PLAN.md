<objective>
Close the loop: detect that the radio has regained service (D-15) and fire the recovery mechanism
the Plan 01 risk gate selected (D-12), then verify the whole phase on a physical device.

Purpose: everything before this plan makes recovery *possible* — one always-proxied style, a
redirect on miss, `Reason::Connection` instead of a poisoned 404. But nothing yet notices that
service came back. `onlineStatusProvider` is optimistic-`true` and moves only when API traffic
happens to succeed or fail, so a hiker standing still with the map open would sit offline until
some unrelated request fired. RESEARCH.md's secondary defect and 39-PATTERNS.md's second flagged
gap are the same thing: the probe exists, the trigger does not.

The mechanism is deliberately not `connectivity_plus`. This project has no such dependency and has
tuned itself hard against radio wakeups (see `_providerRetry`'s comment in `main.dart`). A probe
loop that runs **only while the app already believes it is offline** costs nothing in the common
case, and while offline it fails at the socket level with no route to take — `isBackendReachable`
explicitly "returns immediately when there is no route at all". Interface state would also be the
wrong signal: this app's definition of online is backend reachability, not a radio bar.

Output: a bounded offline probe loop, the recovery trigger wired to the existing false->true
listener, and a developer-run device verification of ROADMAP criteria 1, 2, 5 and 6.
</objective>

  <action>
Add a while-offline probe loop to `_MainAppState`, reusing the connectivity plumbing that already
exists rather than adding a dependency.

Declare `Timer? _offlineProbeTimer;`, `int _offlineProbeAttempt = 0;` and a top-level
`const List<Duration> kOfflineProbeBackoff = [Duration(seconds: 5), Duration(seconds: 10), Duration(seconds: 20), Duration(seconds: 30)];`
whose last entry repeats indefinitely.

Extend the existing `_onlineStatusSub` listener body: when `next == false`, call
`_scheduleOfflineProbe()`; when `prev == false && next == true`, call `_cancelOfflineProbe()`
before the existing `drainIfOnline()` call (Task 2 adds the recovery trigger at the same edge).

`_scheduleOfflineProbe()` is idempotent — return immediately if `_offlineProbeTimer != null`. Do
not schedule at all when `!ref.read(apiProvider.notifier).isConfigured`, because `refresh()`
no-ops in that state and the loop would spin without ever learning anything. Otherwise schedule a
one-shot `Timer` for `kOfflineProbeBackoff[min(_offlineProbeAttempt, kOfflineProbeBackoff.length - 1)]`,
and in its callback: clear `_offlineProbeTimer`, increment `_offlineProbeAttempt`, `await ref.read(onlineStatusProvider.notifier).refresh()`,
and if the result is still false and the state is still `mounted`, schedule again. A successful
probe sets the provider to `true`, which drives the listener above, which cancels the loop — so
the success path needs no explicit rescheduling logic.

`_cancelOfflineProbe()` cancels and nulls `_offlineProbeTimer` and resets `_offlineProbeAttempt`
to 0. Call it from `dispose()` alongside `_onlineStatusSub?.close()`.

In `didChangeAppLifecycleState`, when the state is `resumed` and `ref.read(onlineStatusProvider)`
is false, reset `_offlineProbeAttempt` to 0, cancel any pending timer and probe immediately — a
device that was in a pocket for an hour should not wait out a 30-second backoff step after the
user wakes it. Keep the existing `drainIfOnline()` call unchanged.

Document the design choice directly above the fields: the loop exists because nothing else
re-probes on regain (D-15); it runs only while the app already believes it is offline, so it costs
nothing in the common case; while offline the probe fails at the socket level with no round trip,
which is why a poll is affordable here where a periodic poll while online would not be; and
`connectivity_plus` was deliberately not added, both because this app defines "online" as backend
reachability rather than interface state and because it has no such dependency today.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network -> connectivity decision | a hostile or captive network controls whether `/health` answers, and therefore when the recovery trigger fires |
| app lifecycle -> timer ownership | a timer outliving its `State` would keep probing after teardown |
| app -> MapLibre global connectivity gate | the recovery trigger mutates process-wide MapLibre state (pulse variant) or forces a full style reload (fallback variant) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-39-34 | Denial of Service | battery drain from the probe loop | mitigate | The timer only exists while `onlineStatusProvider` is `false`; it is cancelled on the first success and in `dispose()`; backoff is capped at 30 s; and it never schedules while the api client is unconfigured. While genuinely offline the probe fails at the socket level with no route, so it costs no radio wakeup beyond a failed connect. |
| T-39-35 | Spoofing | a network that can make `/health` answer arbitrarily | accept | The worst an attacker achieves is triggering extra recovery events, which only make MapLibre re-request tiles it already wanted. The probe carries no secret and grants no authority; `isBackendReachable` already treats any answer, including a 404, as "reachable" by design. |
| T-39-36 | Denial of Service | recovery firing in a tight loop | mitigate | The trigger is edge-driven (`prev == false && next == true`) on a `listenManual` subscription with no `fireImmediately`, so a steady state — online or offline — produces no events at all; only a genuine transition fires. |
| T-39-37 | Tampering | connectivity awareness leaking into the proxy | mitigate | D-03 is asserted by an acceptance criterion grepping `tile_proxy_server.dart` for any connectivity symbol; the recovery trigger lives entirely in `main.dart`. |
| T-39-38 | Repudiation | shipping an unverified recovery path | mitigate | Task 3 blocks on developer-reported device outcomes for the four device-observable ROADMAP criteria, and requires FAILs be recorded verbatim rather than reasoned away. |
| T-39-SC | Tampering | npm/pip/cargo/pub installs | accept | This plan adds zero package-manager dependencies — asserted by a `git diff pubspec.yaml pubspec.lock` acceptance criterion, which is also how D-15's "weigh a new dependency against the app's current stance" is settled. |
</threat_model>
